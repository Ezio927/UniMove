# 活动收藏功能设计

## 背景与目标

UniMove 已具备用户认证、活动浏览、报名、订单、评论和个人中心等核心模块。本次以既有项目为基线，新增一个范围可控但覆盖前端、后端与数据库的“活动收藏”功能，用作课程要求的规范化增量开发案例。

目标是让登录用户收藏感兴趣的活动、取消收藏，并在个人中心查看收藏列表。实现应沿用现有 React、Express、Mongoose、JWT 和 Vitest 技术体系，不引入新的运行时依赖。

## 范围

### 包含

- 登录用户收藏一个仍然存在的活动。
- 登录用户取消收藏活动。
- 重复收藏和重复取消均保持幂等。
- 活动列表和活动详情页显示收藏操作。
- 个人中心展示当前用户收藏且仍然存在的活动。
- 收藏相关 HTTP 接口使用现有 JWT 中间件保护。
- 后端服务、接口行为和前端关键交互具有自动化测试。

### 不包含

- 多收藏夹或收藏分类。
- 收藏数量排行、推荐算法或通知。
- 未登录用户的本地收藏。
- 因收藏行为修改报名、订单或评论流程。
- 为历史删除活动保留收藏快照。

## 方案选择

在 `User` 文档中增加 `favoriteActivities` 字段，保存活动 ObjectId 数组。相较独立 Favorite 集合，这种方案需要更少的模型和查询，符合当前项目规模；相较浏览器本地存储，它能够跨会话保存并形成完整的服务端功能。

当项目未来需要收藏时间、收藏夹分类或大规模行为分析时，再迁移为独立关联集合。本次不为尚不存在的需求预先增加复杂度。

## 架构与职责

### 数据模型

`User.favoriteActivities` 是引用 `Activity` 的 ObjectId 数组，默认值为空数组。数据库更新使用集合语义：收藏使用 `$addToSet`，取消收藏使用 `$pull`，以保证重复请求幂等。

### 后端服务与接口

收藏业务进入现有用户服务层，控制器只负责读取认证用户和路径参数、调用服务并返回响应。

提供三个受保护接口：

- `GET /api/users/favorites`：返回当前用户仍然存在的收藏活动。
- `PUT /api/users/favorites/:activityId`：收藏活动；活动不存在时返回 404。
- `DELETE /api/users/favorites/:activityId`：取消收藏；目标未收藏或活动已不存在时仍返回成功结果。

列表查询只返回能够成功关联到 Activity 的记录，因此活动删除后不会在界面中显示无效收藏。无需在删除活动时扫描所有用户文档。

### 前端

用户 API 模块封装读取、收藏和取消收藏请求。活动卡片和详情页根据活动 ID 是否存在于当前用户收藏集合中显示收藏状态。未登录用户触发收藏操作时，沿用现有登录引导方式。

个人中心新增“我的收藏”区域，复用活动卡片的展示能力。加载失败时显示明确错误和重试入口；空列表显示无收藏提示。

## 数据流

1. 用户登录后进入活动列表、详情页或个人中心。
2. 前端读取当前用户收藏列表，并以活动 ID 推导按钮状态。
3. 用户点击收藏或取消收藏，前端调用对应接口。
4. 后端认证用户，校验活动 ID，并通过原子更新修改用户文档。
5. 前端在请求成功后刷新本地收藏状态；失败时保留原状态并显示错误消息。

## 错误处理与安全

- 未认证请求返回 401。
- 非法 ObjectId 使用现有错误边界返回 400。
- 收藏不存在的活动返回 404。
- 数据库异常进入现有集中错误处理中间件。
- 客户端不自行构造或持久化额外凭据，继续使用现有 JWT 流程。
- 接口不允许操作其他用户的收藏集合。

## 测试策略

开发遵循测试先行的红—绿—重构循环。

后端测试覆盖：首次收藏、重复收藏、取消收藏、重复取消、不存在活动、收藏列表过滤失效引用以及未认证访问。优先测试服务层的原子更新规则，并为路由认证和参数传递保留接口级测试。

前端测试覆盖：未收藏与已收藏按钮状态、点击后调用正确 API、失败后保留原状态，以及个人中心的加载、空状态和收藏列表渲染。

完成后运行前后端 lint、类型检查、测试和构建，并通过根目录统一验证命令及 CI 再次执行。

## 完成标准

- 三个收藏接口行为符合上述约定。
- 活动列表、活动详情和个人中心可以完成收藏相关用户流程。
- 重复操作不会产生重复收藏或错误状态。
- 新增测试能够证明关键规则，并与现有测试一起通过。
- 不提交真实凭据，不增加新的运行时依赖。
- 相关实现、测试、文档和过程记录可由独立提交追踪。
